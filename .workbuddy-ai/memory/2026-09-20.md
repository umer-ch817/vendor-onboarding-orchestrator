## User question: is an OpenAI-compatible endpoint needed? (answer: no)

User supplied an OpenAI-compatible proxy at `http://localhost:20128/v1`, key
`sk-42f9...`, model `auto/best-free`, and hit
`ECONNREFUSED ::1:20128` from n8n. Investigated:

- **No AI/LLM node exists in any of the 4 n8n workflows.** Node types are only
  httpRequest, code, set, if, switch, webhook, scheduleTrigger, errorTrigger.
  The credential error came from something the user added themselves in the n8n UI.
- **The proxy is alive and the key works** — `/v1/models` returns 401 without the
  key, 4710 models with it, and `auto/best-free` is present.
- **Why it fails from n8n anyway:** n8n runs in Docker. `localhost` inside the
  container is the container itself (and Node resolves it to `::1` first). The
  compose file already uses `host.docker.internal:8000` for the backend for
  exactly this reason. From a container you must use `host.docker.internal`, not
  `localhost`.
- **The backend's LLM is optional and defaults to mock.** `LLM_PROVIDER=mock` in
  `.env`; `backend/app/ai/provider.py:get_provider()` falls back to MockProvider
  when no key is set. `AI_RISK_ANALYSIS` audit events come from the mock, so the
  workflow works with zero network and zero key.
- **The backend cannot use a custom base_url as written.** `OpenAIProvider` builds
  `AsyncOpenAI(api_key=..., timeout=...)` with no `base_url` — it always targets
  api.openai.com. Wiring the user's proxy requires adding an `OPENAI_BASE_URL`
  setting and passing `base_url=`. Also note `json_mode` defaults to True, which
  sends `response_format: {"type":"json_object"}` — not every proxy honours it.
  The backend runs natively on the host (not in Docker), so `localhost:20128`
  *would* be reachable from it.

## Wired up the real AI (user's OpenAI-compatible gateway)

Added `OPENAI_BASE_URL` to `Settings` and `OpenAIProvider` (was hardcoded to
api.openai.com). Client is built with `base_url` only when set, so the SDK
default is preserved. Added a `json_mode` fallback: if a gateway 400s on
`response_format`, retry once without it and let `parse_json()` find the object.

**Three obstacles, in the order hit:**
1. `localhost` resolved to `::1` (proxy listens on IPv4 `0.0.0.0` only) — not
   actually the blocker; `127.0.0.1` also failed.
2. **The real blocker: `HTTP_PROXY`/`HTTPS_PROXY` are set in this environment.**
   httpx forwarded the loopback request to the proxy → `TooManyRedirects`.
   Fixed with `_targets_loopback()` in provider.py: when the base URL is
   loopback, build the client with `httpx.AsyncClient(trust_env=False)`.
3. `auto/best-free` is advertised by the gateway but fails upstream (403
   OpenCode free tier / 429 Felo). Probed alternatives; `auto`, `auto/best-fast`
   and `auto/best-coding` all work. Settled on `auto/best-fast`.
   The gateway routed it to `gemini-3.7-flash-high`; ~12-22s per call.

## Two genuine bugs found only by running it for real

- **Document upload was broken: HTTP 400 on every upload.**
  `logger.info(..., extra={"filename": ...})` — `filename` is a reserved
  LogRecord attribute, so makeRecord raised KeyError. 5 log call sites fixed
  (`filename` → `document_filename` in extraction.py x4, documents.py x1) plus
  `"message"` → `"incident_message"` in webhooks.py. Reserved-attr list is now a
  single constant `RESERVED_LOG_RECORD_ATTRS` in utils/logging.py, shared by the
  JSONFormatter and a new AST-scanning regression test. Note the ~10 other
  `"filename"` keys in rules/engine.py are `evidence=` data dicts, not log extras
  — leave them alone.
- **n8n HTTP nodes 404'd.** `Process Document` / `Verify Extraction` /
  `Submit Case` / `Run Assessment` built URLs from `$json.document_id` /
  `$json.case_id`, but they are chained *after* a callback node whose payload is
  `{recorded, event_id, ...}` — no id. URL became `/api/documents//process`.
  Fixed to `$('Validate Trigger').first().json.<id>`. Also raised the shared
  `timeout_ms` default 30000 → 180000 (a real model takes ~40s per document; the
  30s limit produced `RETRY_EXHAUSTED` for requests that were still working).

## Answered: does the UI need n8n? (no)

- `frontend/src` has zero n8n references — it only reads the backend. The only
  "n8n" in the UI is an actor label in the audit timeline.
- The backend already exposes `POST /api/onboarding/{id}/submit` and
  `/{id}/assess` — the *same* endpoints the n8n workflow calls. So the backend
  can run the whole assessment alone; n8n adds approvals, notifications, SLA
  escalation and error handling on top.
- `http://localhost:8000/docs` (Swagger, 200) is a clickable way to run
  everything with no n8n and no curl. Frontend runs on :5173.
- `N8N_WEBHOOK_URL` already exists in config but nothing reads it — that is the
  natural place to hang a "start onboarding" button if the UI should trigger n8n.
